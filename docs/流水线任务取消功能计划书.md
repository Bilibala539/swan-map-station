- 负责人:主会话(计划/部署/验收/提交) · swan-pipeline(全链路实现) · swan-designer(交互细则+图标)
- 状态:**✅ 全部落地(2026-09-22)** M-A/B/C/D/B2 已入库(de65e8f),M-E 真机验收六项全过,详见第八节验收记录

## 一、背景与问题

pipeline_jobs 现有生命周期只有 create → claim → finish(`server.py:1104-1206`),没有 cancel。
任务一旦开跑,设备被占满跑到底(20-30 分钟),平台侧无任何停止手段,唯一出路是登 Jenkins 手动 abort。

实际受损场景:误触发套件、白天临时要占用手机、验证过程中发现跑错想中途停。

## 二、目标 / 非目标

**目标**
1. pending 与 running 状态的流水线任务可从平台页面取消
2. 取消后设备及时归还,.176 上 pytest 进程终止,任务状态准确落库
3. 部分结果保留:取消前已上报的用例结果可见,run 标记"已取消";**统计口径:已取消的 run 不计入通过率分母**(取消≠执行结论,避免误触发+取消拉脏统计),run 内已上报用例结果如实展示
4. agent 离线时的取消兜底(平台侧超时强制取消)

**非目标**
- 不做 Jenkins 侧打包 job(swanaudio-build)的取消入口(打包仅几分钟,由平台 dispatch 已有链路覆盖;后续有需要再议)
- 不做批量取消、定时任务(流水线配置)的取消
- 不做取消后断点续跑

## 三、用户场景

| 场景 | 现状 | 目标 |
|---|---|---|
| 误触发,任务还在排队(pending) | 无法阻止,只能等它跑 | 一键取消,任务直接"已取消",永不下发 |
| 任务运行中(占用设备) | 只能等 20-30 分钟 | 点取消→"取消中"→设备归还→"已取消" |
| agent 掉线,任务卡 running | 现有 stale-claim 超时接管(error) | 取消请求超时后平台强制落"已取消"并释放设备 |

## 四、状态机

```
pending ──取消──> cancelled(直接落库,claim 只领 pending,天然不再下发)
pending ──claim──> running ──finish──> success/failure/error(现状不变)
running ──用户点取消──> cancelling(平台置 cancel_requested=1)
cancelling ──agent 确认(finish status=cancelled)──> cancelled
cancelling ──超时(>5 分钟无 agent 回报)──> cancelled(平台强制,释放设备)
```

规则:
- 取消仅允许 pending/running/cancelling 之外的态返回 409
- finish 带状态条件更新(`UPDATE ... WHERE status='running'`,沿用 server.py:799 幂等模式),取消与正常完成竞态时先到先得
- 'cancelling' 态的任务在流水线任务列表显示"取消中"胶囊;agent 每次轮询间隔内即可看到旗标

## 五、交互设计要点(swans-designer 出终稿,落规范 6.3 + 4.1)

1. 入口:流水线任务列表(pl-job-rows)running/pending 行尾新增**取消图标按钮**(circle-x 样式,danger 红;图标已审并加入规范 4.1 白名单第 8 枚,M-A 完成,SVG 见规范)
2. 点击走统一确认弹窗(cfm-modal),文案按行状态两支(M-A 细化,两态后果不同正文须如实):pending="取消任务 JOB-XXX?任务尚未开始,取消后不再下发";running="取消任务 JOB-XXX?运行中的用例将中断,已产出结果保留"
3. 状态胶囊:'cancelling'→"取消中"(警示色 --warn,纯状态徽章不可点击——原"可点击无操作"表述废弃,死交互违反规范 4.8 badge/chip 分工)/'cancelled'→"已取消"(中性灰 --muted);success/failure/error 胶囊样式不变。色板语义详见规范 2.2/6.3
4. pending 行取消后行内状态直接变"已取消";running 行取消后按钮变禁用直至终态
5. 取消后的任务行保留 Jenkins 日志按钮(如已回填 build 号)——排查用了多少时间、跑到哪

## 六、技术方案

### 6.1 数据模型
- `pipeline_jobs` 增列:`cancel_requested INTEGER NOT NULL DEFAULT 0` + `cancel_requested_at TEXT`(兜底 5 分钟计时起点,M-B 实现补充)(ALTER TABLE 迁移,带存在性守卫)
- 状态值集合扩为 pending/running/cancelling/cancelled/success/failure/error
- runs 侧 'cancelled' 状态归执行与证据模块扩展(M-B2,与 M-C 串行避免同文件并发)

### 6.2 API(server.py)
- `POST /api/pipeline/jobs/{job_id}/cancel`:404 不存在;409 非 pending/running;pending→直接 cancelled;running→置 cancel_requested=1 + status='cancelling',返回 {ok, status}。**实现注记(M-B)**:允许空请求体,路由先于 read_json 分流(对齐 config-run 先例)
- `GET /api/pipeline/jobs/{job_id}`(如已有则复用):agent 轮询用,返回含 cancel_requested;注意 agent 鉴权与现有 _post 通道一致
- finish 通道:接受 status='cancelled'(agent 上报),处理逻辑复用现有 finish_pipeline_job 的设备释放与 run 收尾。**实现注记(M-B,立项后追加拍板)**:finish 改状态条件更新 `WHERE status IN ('running','cancelling')`(取消 vs 正常完成竞态先到先得);cancelled 落库时**平台按 current_run=pipe-{job_id} 统一释放设备**——pytest 被看门狗杀掉时 conftest 的 sessionfinish 不会执行,设备归还必须平台侧做

### 6.3 平台侧(两条执行通道,pytest 都是 .176 上 agent 的本地子进程)
- **本地轮询通道**(--loop daemon):agent 轮询旗标后自行终止子进程并回报
- **Jenkins 定向通道**(swan-autotest 构建 → `pipeline_agent --job-id`):agent 同样轮询旗标;agent 退出即构建结束(预期红,notes 标 cancelled);jenkins_client 增 `stop(job, build)`(POST /job/{job}/{build}/stop)备用——打包阶段已被排除在范围外,此方法仅作 agent 兜底手段,可后置
- pending 直接取消时无需通知任何执行侧(claim 只领 pending;定向通道对已取消任务 404 空跑退出,pipeline_agent.py:378 已天然兼容)

### 6.4 agent 侧(pipeline_agent.py)
- execute_job 期间起 watchdog 线程:每 5s GET 任务详情,见 cancel_requested=1 即终止 pytest **进程组**(.176 Linux,os.killpg;注意 pytest 可能派生子进程/adb 调用,必须整组杀)
- 终止后按现有 finish 通道回报 status='cancelled',设备由平台 finish 逻辑统一释放
- watchdog 自身异常不影响主流程(降级为不响应取消,由平台超时兜底)
- **实现注记(M-C)**:`_terminate_proc_group` SIGTERM 整组→8s 仍活→SIGKILL 升级(adb 卡死兜底),Windows 退化为单进程 terminate;execute_job 三检查点分流(装包后/首轮后/--lf 重跑后)见旗标即走 `_finish_cancelled`;run 已建时补 complete 收尾,上报状态走 `RUN_COMPLETE_STATUS_ON_CANCEL` 常量——**现值 'error',runs 侧枚举扩 cancelled 后(M-B2)由主会话统一切 'cancelled'**;run 未建(pytest 未启动即取消)时 complete 404 容忍

### 6.5 超时兜底与竞态
- 平台启动时/周期任务:status='cancelling' 且 cancel_requested 超过 5 分钟 → 强制 cancelled + 释放设备(复用 server.py:186 stale-claim 接管模式)。**实现注记(M-B)**:阈值 = `CANCEL_STALE_MINUTES`(默认 5,环境变量可覆盖),计时起点 = cancel_requested_at 置位时刻;`_force_cancel_stale` 挂 claim 惰性回收,幂等,与 agent 迟到的 finish 先到先得
- 取消 vs finish 竞态:两者都带 WHERE status 条件,先到先得,后到方无副作用

## 八、验收标准

1. pending 任务取消:列表即变"已取消",agent 不执行(本地与 Jenkins 定向两通道各验一次)
2. running 任务取消:≤10s 内 pytest 进程消失,设备归还(设备表回到 free),任务"已取消",已上报用例结果保留可查
3. agent 离线时取消:5 分钟后平台强制落"已取消",无僵尸 cancelling 态
4. 正常完成与取消竞态:不出现双写/状态回跳
5. 既有路径回归:正常跑一轮流水线全绿,列宽拖拽/图标按钮不回归
6. 统计口径:被取消 run 不改变通过率统计卡的数值;run 详情内已上报用例结果照常可查
