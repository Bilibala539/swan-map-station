## 一、设计原则与交互理念

> 2026-09-22:本节由 v1.0 四条设计原则体系化而来(原第 1/2/3 条分别收编进理念 2/1/4,原第 4 条保留为下方风格红线)。来源两条线:经典 HCI(Nielsen 十启发式/Gestalt/认知负荷/Fitts/data-ink ratio/NN/g 渐进披露)+ 产品实证(Linear/Stripe/Vercel/GitHub/AWS 反面/本站竞品采集 4 家,出处见 1.2)。**定位:此后所有页面设计的取舍都应能回溯到这七条理念;发现某条理念在真实页面落不了地,回来修理念,不许绕过它。**

### 1.1 交互理念(七条,取舍总依据)

#### 理念 1 状态即颜色,一色一义

**理念**:颜色只编码状态;一个颜色全站只有一个含义,同一状态全站只用一种视觉形态(点/徽标/文字色),不因页面而异。
**依据**:Nielsen 十启发式第 4 条"一致性与标准"(NN/g, 1994);Gestalt 相似律——视觉相同的元素被感知为一类(Wertheimer, 1923)。反面实证:AWS 控制台被批评多年的核心正是"同一状态在不同服务呈现为不同视觉格式",用户被迫逐处重学(TechRepublic 2023 控制台对比、r/aws 2022-2024 讨论);AWS 2024 官方改进清单第一条即"统一状态徽标配色"。
**判据**:2.2 语义色表是唯一分配表(红=失败/绿=通过/蓝=进行中/黄=跳过等待),新用色先查表;纯分类(服别/类型)不占用语义色(2.4);同一状态不混用点/徽标/裸文字色三种形态;状态色必须配文字标签,不许裸色传达(色弱可读)。

#### 理念 2 密度服务扫描,装饰让位数据

**理念**:工具页第一任务是扫读;装饰元素默认预算为零,只有帮读数的例外(如数字对齐)。
**依据**:Tufte《The Visual Display of Quantitative Information》(1983) data-ink ratio——墨水花在数据上;Stripe 官方文档采用 `font-variant-numeric: tabular-nums` 让金额列垂直对齐(docs.stripe.com/guides/money-formatting);Linear 用 32-36px 紧凑行支撑大列表分诊——密度=更少滚动=更快分诊,感知速度本身是设计决策。
**判据**:表格用 3.2 紧凑档(td 9px 12px、无斑马纹);数字列右对齐+tabular-nums;ID/路径等宽字体;装饰预算=卡片单层极淡阴影,渐变/玻璃拟态/大图标一律不做;加列前先回答"这一列帮用户做什么决定",答不上就不加。

#### 理念 3 渐进披露:列表给扫描层,细节按需展开

**理念**:列表只放扫读所需的信息量;细节、编辑、低频信息收到下一层,披露颗粒度跟随工作流,不为藏功能而藏。
**依据**:认知负荷理论(Sweller, 1988)与工作记忆容量(Miller, 1956, 7±2);NN/g《Progressive Disclosure: 2 Examples》(Whitenton, 2014)——同时警告:映射不了工作流的披露=无意义点击。
**判据**:列表默认可见列 ≤7±2;详情/编辑收抽屉或弹窗(4.3/4.4),不做行内展开编辑;次要信息降级为次行灰字或 title;展开内容与列表有明确主从,不平行铺开。

#### 理念 4 展示态与编辑态分离

**理念**:读的界面里只有读的东西;改是另一个明确的模式,进得去出得来。
**依据**:Nielsen 第 3 条"用户控制与自由"、第 5 条"防错优于报错"(NN/g, 1994);模式错误(mode error)——只读流混入编辑控件时误触率上升(Norman《The Design of Everyday Things》, 1988)。
**判据**:列表页只读;编辑收抽屉/弹窗(5.3);删除等危险动作一律确认弹窗 + Danger 文字链(4.1/4.5);行内编辑不做(小团队维护不起两套渲染)。

#### 理念 5 每区块一个主动作

**理念**:一个决策区块内,视觉重量最高的动作只有一个,其余全部降级——让"最该点的按钮"自己站出来。
**依据**:Fitts 定律(Fitts, 1954)——目标越大越近命中越快,主动作必须最大最显眼;Nielsen 第 6 条"识别优于回忆"(NN/g, 1994)——按钮动宾结构自解释;Linear 的 opinionated defaults 路线——约束让决定更快。
**判据**:Primary 每区块 1 个(跨区块不累计、同区块禁两个,4.1);Ghost 不限;Danger 只做行内文字链;按钮文案=动词+宾语("登记 APK",不写"确定/提交")。

#### 理念 6 空态是路标,不是插画位

**理念**:空态回答三件事——这是什么状态、为什么、下一步做什么;装饰不在答案里。
**依据**:NN/g 空态指导——纯插画空态是可用性失败,文字解释+可行动是底线;实证 Vercel 空态=标题+一句话+CTA+可复制命令,直接压缩首次部署耗时。
**判据**:空态=一句灰字说明+(可选)一个 ghost 按钮,居中;插画/emoji 禁止;区分三种文案——没有数据/筛选无结果/加载失败,不共用"暂无数据"。

#### 理念 7 反馈轻量,异常可见

**理念**:操作反馈要轻(不打断),系统异常要显(不隐藏)——失败的数据也是数据。
**依据**:Nielsen 第 1 条"系统状态可见"(NN/g, 1994);Doherty 响应时间研究(IBM, 1982)——亚秒响应才感知即时,超时必须有进行中指示;实证 GitHub recovery codes 对已消费代码降灰加"已用"标记而非隐藏——已用几张直接影响"还剩几个码"的决策。
**判据**:alert/confirm 全替换(4.5,P0);操作结果用 Toast,长任务给进行中状态而非转圈遮罩;加载失败给原因+自动重试说明;过期/已消费/失联数据降灰保留不隐藏;轮询仅在页签激活时进行(5.5)。

### 1.2 参考来源与借鉴纪律

**经典**:Nielsen 十启发式(NN/g, 1994)/Gestalt 组织原则(Wertheimer, 1923)/Fitts 定律(Fitts, 1954)/认知负荷(Sweller, 1988)/工作记忆 7±2(Miller, 1956)/data-ink ratio(Tufte, 1983)/渐进披露(NN/g Whitenton, 2014)/模式错误(Norman, 1988)/响应时间阈值(Doherty, IBM, 1982)。
**产品实证**:Linear(低噪状态 chip、紧凑行、约束即特性)/Stripe(tabular-nums 官方文档、淡底 pill 徽标、小灰表头)/Vercel(Geist、语义状态点、可行动空态)/GitHub(等宽 ID、recovery codes 已消费标记;本站采集分析 docs/竞品截图/auto/github-releases.md)/AWS 控制台(反面教材:状态格式不一致、跨服务无统一组件,恰是理念 1 的实证)/蒲公英·Diawi·fir.im(下载分发场景,docs/竞品截图/auto/ 三家采集,2026-09-20)。
**借鉴纪律**:每家只取能回溯到理念的最值得搬的一两点,消化进本站 token 体系;不照抄配色,不搬整套视觉;堆渐变玻璃拟态那套(设计圈模仿"Linear 风格"的产物)恰是我们要反的。

> ### 杜绝"一眼 AI"设计风格(硬性红线)
> - **不用大面积渐变。** 全站一律平色——含页头 header(2026-09-22 深审撤销 v1.0 的"页头一处现状保留"条款:深蓝渐变大 banner 是用户点名"一眼 AI"的第一嫌疑,header 改平色 `var(--ink)` 白字)。禁止紫蓝渐变、渐变按钮、渐变文字。
> - **界面文案不堆 emoji。** 状态用徽章色表达,不用 ✅❌🚀 等字符装饰(现有 `apk-msg` 的 "✅ 已登记" 要改为 toast+语义色)。标题、按钮、空状态一律纯文字。
> - **圆角与阴影收敛为固定档位。** 圆角三档:输入框/按钮 8px、卡片/抽屉/弹窗 10-12px、状态徽章胶囊 999px。阴影两档:卡片 `0 2px 10px rgba(23,32,51,.03)`,浮层(弹窗/下拉/抽屉)`0 8px 24px rgba(23,32,51,.14)`(侧滑抽屉可用方向性 `-8px 0 30px` 同 alpha)。禁止发光、毛玻璃、玻璃拟态。**阴影语义 tint 档(2026-10-12 增补)**:异常焦点卡可用语义色 tint 双层阴影 `0 1px 2px rgba(语义色,.08), 0 6px 16px rgba(语义色,.07)`(巡检红卡实证:`0 1px 2px rgba(201,42,42,.08), 0 6px 16px rgba(201,42,42,.07)`);仅限**全页唯一重物**的异常元素,普通卡片仍用两档中性阴影。**状态反馈动效曲线(2026-10-12 增补)**:边框/底色/阴影/滑入等状态反馈过渡统一 `cubic-bezier(.32,.72,0,1)`、时长 0.12-0.22s;装饰性动效仍然不做——本条澄清"为做而做的动效"禁令的边界:反馈类过渡合规。**散值收敛对照(2026-09-22 深审)**:存量越档值 2px(mark)/6px(.link-danger/#cdd-file-path)/7px(.cd-pill)/9px(.cd-pills) 分别收敛为 删除/8px/8px/10px;toast 阴影 .24 与抽屉 .18 统一到 .14;拖拽指示 `inset 2px 0 0` 属功能指示非装饰,不算阴影档。
> - **空状态不加插画和大标语。** 空状态 = 一句灰字说明 + (可选)一个 ghost 按钮,居中,完事。禁止卡通插图、禁止"暂无数据,快来开启美好旅程"式文案。
> - **文案用测试工程师的语言。** 写"失败 3 条"、"下次执行 02:00",不写"智能调度""一键赋能""极致体验"。数字对齐、单位统一,比任何修辞都重要。

## 二、色彩系统

### 2.1 基础 token(现状保留,新增补充)

```css
:root {
  /* 现有 */
  --ink:#172033; --muted:#5d6a80; --line:#e6e9ef; --bg:#f5f7fb;
  --card:#fff; --brand:#405cf5; --good:#087f5b; --bad:#c92a2a; --warn:#915f00;
  /* 2026-10-19 UIB-05:--muted #667085→#5d6a80、--warn #ad6800→#915f00(同色相压暗),弱底上对比度达 WCAG AA 4.5:1 */
  /* 新增:语义色弱底(把散落在各 badge 类里的硬编码收进 token) */
  --good-weak:#e6fcf5; --bad-weak:#fff5f5; --brand-weak:#edf2ff; --warn-weak:#fff9db;
  --neutral-weak:#f1f3f8;              /* 中性徽章/chip 底 */
  --hover:#f8f9ff;                     /* 行悬浮 */
  --danger:#c92a2a;                    /* =--bad 的别名,用于危险按钮,便于语义检索 */
}
```

规则:弱底色只和它的强色配对使用(good 只配 good-weak),不许交叉;文字永远用强色(弱底上放弱色字对比度不够)。深色文字不用纯黑,一律 `--ink`。

### 2.2 状态语义色(执行结果的唯一呈现方式)

| 状态 | 文字/图标色 | 底色 | 现有类 |
|---|---|---|---|
| 通过 passed | `--good` | `--good-weak` | `.passed` |
| 失败 failed / 错误 error | `--bad` | `--bad-weak` | `.failed` `.error` |
| 执行中 running | `--brand` | `--brand-weak` | `.running` |
| 跳过 skipped / 等待 pending | `--warn` | `--warn-weak` | `.skipped` |
| 阻塞 env_blocked | `--warn` | `--warn-weak` | 新增,文案"环境阻塞" |
| 取消中 cancelling | `--warn` | `--warn-weak` | 新增,文案"取消中";过渡态(等待 agent 确认/平台 5 分钟兜底),流水线任务取消(6.3) |
| 取消 cancelled | `--muted` | `--neutral-weak` | 新增,文案"已取消" |
| 待分析 pending_analysis | `--warn` | `--warn-weak` | 新增(6.10 AI 任务看板),文案"待分析" |
| 疑问待答 questioning | `--warn` | `--warn-weak` | 新增(6.10),文案"疑问待答" |

AI 任务看板(6.10,v1.1 按用户拍板修订)把 warn 族语义收敛为一句话:**黄=等人,蓝=在跑,绿=成了,红=砸了,灰=关了**——本模块仅"待分析/疑问待答"两个等人态用 warn 族,完成/失败直接复用 `.passed/.failed` 与执行会话同形;不为此发明新色。**撤销记录**:v1.0 曾规划的"待审批/待处理冲突/已驳回"三态随人工审批闸门删除而取消(高风险放行与合并决策由 AI 自主),合并冲突降级为任务属性 merge_status(任务保持"执行中"),不再占状态。

所有状态一律走 `.badge` 胶囊(现有样式:`border-radius:999px; padding:3px 9px; font-size:12px; font-weight:600`)。新增状态只加类,不改组件。

**巡检/机器监控语境的语义色背书(2026-10-12 v0.6 定稿,巡检流程总览见 6.9)**:上表四色语义延伸到巡检语境,不新增颜色——绿=正常,与"已自愈"同用绿族、靠文案区分(自愈是终态"成了",不引入新色;蓝保持全站"执行中"语义,巡检不占用);黄=未纳巡检(合规提示,与跳过/等人同族);灰=无数据/暂不可判/受影响(数据源缺失时诚实降灰,不判好坏,理念 7);红=异常,且巡检总览的异常环节卡是**全页唯一重物**——页面上唯一同时带边框+语义 tint 阴影(红线区条款)+17px 环节名的元素,红色焦点由其他元素的减法达成,不靠红卡自身加装饰。状态一律点/胶囊+文字标签,不裸色。

### 2.3 优先级四档配色(用例管理/套件统一)

现状优先级是自由文本("P0 / P1 / L2 / L3"),规范为四档,旧值入库时映射(L2→P2,L3→P3,L1→P1;非标值归 P3 并在抽屉里提示):

| 档位 | 文字色 | 底色 | 说明 |
|---|---|---|---|
| P0 | `--bad` | `--bad-weak` | 冒烟级,主流程 |
| P1 | `--warn` | `--warn-weak` | 核心功能 |
| P2 | `--brand` | `--brand-weak` | 一般功能 |
| P3 | `--muted` | `--neutral-weak` | 边缘/低频 |

统一用现有 `.chip.lvl` 容器换色,徽章文案就是 `P0`~`P3`。**不要**给 P0 加边框加粗、加感叹号——颜色档位已经足够,叠装饰就是"一眼 AI"。

**风险三档(AI 任务,2026-09-29)**:分析结论的风险等级属"severity 型分类",与 P0-P3 同理允许语义色——高风险=`--bad`/`--bad-weak`、中风险=`--warn`/`--warn-weak`、低风险=`--muted`/`--neutral-weak`,chip 文案"高风险/中风险/低风险"。**v1.1 注:风险是纯展示信息**(提示"这单动了要紧的东西"),高风险放行与合并决策由 AI 自主,不设人工审批闸门。同页不与失败徽标并排滥用;任务类型(代码修改/测试执行等)是纯分类,走中性 chip(2.4)。

### 2.4 类型/类别徽章

| 类型 | 样式 | 现有类 |
|---|---|---|
| 文字用例 | `#9a6700` 字 / `#fff8e1` 底 / `#efd68b` 边 | `.badge.t-text`(保留) |
| 自动化用例 | `--brand` 字 / `--brand-weak` 底 / `#c3ceff` 边 | `.badge.t-auto`(保留) |
| 套件 smoke | `--warn` / `--warn-weak` | `.su-type-smoke` |
| 套件 regression | `--brand` / `--brand-weak` | `.su-type-regression` |
| 套件 custom | `--muted` / `--neutral-weak` | `.su-type-custom` |
| 套件端(安卓/iOS/鸿蒙) | 全部 `--muted`/`--neutral-weak`,**不配色**——端是纯分类无好坏语义,与 Flavor 同规;三值同款靠文案区分 | 新增 `.badge.su-os` |
| Flavor(test/debug/release) | 全部 `--muted`/`--neutral-weak`,**不配色**——flavor 无好坏语义,配色是噪音 | 新增 `.chip` |
| 服别(包管理页) | 以 apks.server_type 列为准(formal/test):正式服=中性 chip + `--ink` 1px 描边(防呆锚点);测试服=普通中性 chip。语义四色已被状态占用,服别不引入新色 | 新增 `.chip.svr-*`(见 docs/下包页设计.md 4.1) |

原则:**有趋势/好坏含义的才用语义色,纯分类用中性灰。**

### 2.5 图表/统计用色

统计卡数字一律 `--ink`,不做彩色大数字;只有"最近一次状态"这类本身是状态的值才允许上语义色。禁止彩虹色多色系(每页彩色种类 ≤ 4:红绿蓝黄)。

## 三、排版与密度

### 3.1 字号层级(全站只许这五档)

| 层级 | 字号/字重 | 用途 |
|---|---|---|
| 页标题 | 23px / 700 | header h1(现状) |
| 区块标题 | 17-19px / 600 | 抽屉标题 h2、区块 h2 |
| 正文 | 14px / 400 | body 默认、表单控件 |
| 表格与辅助 | 13px | `td`、抽屉正文;`meta/hint/label` 12-13px |
| 表头/徽章/标签 | 12px / 600 | `th`、`.badge`、`.stat-label` |

### 3.2 表格密度(默认紧凑档)

现状 `th,td { padding:12px 15px }` 行高约 47px,信息密度偏低。规范:

- **默认档**:`td` padding `9px 12px`,行高 ≈40px,13px 字;`th` padding `8px 12px`。全站表格统一,包括执行会话、包管理、流水线、套件(现状这几张表和用例管理表密度不一致,要拉齐)。
- **不要斑马纹**:行间已有 `border-bottom:1px solid var(--line)`,再加斑马纹是双重噪音。用行悬浮补扫读:`tbody tr:hover { background:var(--hover) }`(所有表,不只 `.clickable`)。
- 数字列(耗时、用例数、执行次数)`text-align:right; font-variant-numeric:tabular-nums`;ID/commit/包 ID 等主键列用 `font-family:ui-monospace,Consolas,monospace; font-size:12px`。
- `white-space:nowrap` 只用于短列;标题/备注类列 `white-space:normal` 并给 `max-width`(沿用 `.cd-case-title` 的做法)。
- 表格横向溢出:外层容器 `overflow-x:auto`(沿用 `.cd-tablewrap`),页面 body 永不横向滚动。
- 列分隔线与拖柄(2026-10-14 用户审核拍板,样版评审反馈"列边界不清晰、拖柄难找"):每列右缘常显 1px 分隔线(`--line`,表头与数据行一致,末列不加——与卡片边线重合),不再由吸右列阴影承担分界;列宽拖柄 hover 表头右缘显形(主色 3px 拖柄条 + col-resize 光标),拖动全程显示随鼠标的垂直参考线、松手消失。细则见《平台列表列设计规范》3.1/3.2。

### 3.3 页面骨架

- 主内容最大宽 1240px 居中(现状);工具栏 = 左筛选、右主操作(现状结构,保持)。
- 统计卡:数值 22px(现状 25px 偏大)、标签 12px muted;卡片 padding 16px(现状 18px 微收)。
- 区块间距统一 18px(`margin-bottom`),卡片内表单/表格不留额外大空。

何时用:**新建/编辑一条短表单**(字段 ≤ 2 行网格)、**危险操作确认**。中断注意力的场景。

### 4.5 反馈:Toast + 确认弹窗(替换原生 alert/confirm)——全站 P0

现状大量 `alert()` / `confirm()`,观感差且打断。规范:

```css
.toast { position:fixed; top:18px; left:50%; transform:translateX(-50%); z-index:99;
  background:var(--ink); color:#fff; padding:10px 18px; border-radius:10px;
  font-size:13px; box-shadow:0 8px 24px rgba(23,32,51,.24); }
```

- 成功/一般提示:深色 toast,2.4s 自动消失,文案如"已登记包 swan-dev-xxx"。成功 toast 左侧加 8px `--good` 竖条,失败加 `--bad` 竖条——不用 emoji。
- 失败/错误:同样式,3.5s 或手动关。
- 危险确认(删除用例/套件/配置、立即执行):统一确认弹窗——标题写动作("删除流水线配置 PIPE-SMOKE-DAILY?"),正文写后果("成员关系一并删除,此操作不可撤销"),按钮 `ghost 取消 + 实底 --bad 确认`。**替换全部 `confirm()` 调用。**
- 全站统一组件(2026-09-22 深审定稿,单例复用,勿每页各造一个):`#cfm-modal`(fixed 遮罩 rgba(15,23,42,.45) z-62 + `.cfm-box` 白卡 12px 圆角/浮层阴影/宽 min(420px,92vw)/margin 12vh auto,h3"确认操作"+`#cfm-text` 正文+`ghost 取消`+`#cfm-ok` 实底 --bad 确认),显隐沿用全站 hidden+CSS 写法。**结构裁断(2026-09-22 终审)**:dc0f4fa 实现用单层 fixed 容器(#cfm-modal 自带遮罩背景+内嵌白卡),与我最初给的 mask+aside 双层功能等价且少一个节点——**收编单层为准**;点遮罩关闭用 event.target===容器 判定(点白卡不关)。JS `confirmAction(text)` 返回 Promise,6 处 confirm 调用点(删包/删用例/删模块/立即执行/删配置/删套件)以 `if(!(await confirmAction(原文案)))return;` 替换,文案原文照搬。14 处 alert 按双态映射:`showToast(msg)` 成功/一般、`showToast(msg, true)` 失败(流水线"已触发任务"那处成功 alert 也改 toast)。**z 层定 62**(实现回写 2026-09-22):须盖过抽屉 z-61——删除用例的确认弹窗在抽屉打开时也要可达。全站浮层 z 链(2026-09-22 定稿,新增浮层按此插入):抽屉/侧栏 61 < cfm-modal 62 < bug-modal 63(建单表单从抽屉内触发,e61180d 起由 50 升 63)。
- 表单内即时校验仍用现有 `msg` span,但文案规范:"包 ID 必填"这类具体字段名 + 原因,`--bad` 色 12px,不用"输入有误"。

### 4.6 表单

- 布局:`.form-grid` 3 列(窄屏 2 列),label 12px muted 在上、控件在下(现状)。textarea 全宽。
- 控件:白底 `--line` 边 8px 圆角(现状);checkbox/radio 去全局粗边距(现状已处理,保持)。select 高度与 input 一致。
- 必填:label 带 `*`,红色;不做星号以外的强提示。
- 校验:提交时逐字段检查,第一个错误字段聚焦并把错误写到该字段下方 12px 红字(新增 `.field-error { color:var(--bad); font-size:12px; margin-top:4px }`),不再只塞在底部 msg 里;校验失败不清空用户输入。
- 频率设置(流水线弹窗)的 radio + 条件参数显隐交互是正确模式,保持;参数区切换时保留已填值。

### 4.7 空状态与加载态

- 空状态:一行 13px muted 文案说明"为什么空 + 下一步",如"还没有测试套件,点右上角'新建测试套件'创建";可选跟一个 ghost 按钮。禁止插画、禁止大标题。
- 加载态:表格首行沿用"加载中…";按钮提交期间 `disabled + opacity:.5`,防止重复提交(建单/登记包已做,补齐到所有保存按钮)。
- 错误态:接口失败时表格区显示"加载失败:xxx"+ ghost"重试"按钮,不是空白。

### 4.8 徽章与 chip

- `.badge`(状态/类型,胶囊)与 `.chip`(可点/信息,小圆角 999px 亦可但必须 hover 反馈)分工:badge=结果,chip=属性/链接。bug 单 chip 红色系、模块 chip 中性(现状保留)。
- 一格内多个 chip 换行堆叠(现状 `.cd-td-links` 处理方式),上限 3 个 + "…N"。

## 五、交互模式

### 5.1 抽屉 vs 弹窗 决策表

| 场景 | 用什么 | 本站实例 |
|---|---|---|
| 查看用例/会话详情 | 抽屉 | 用例详情抽屉;执行会话详情应从页面下嵌区改抽屉 |
| 复杂编辑/多栏对照(勾成员) | 抽屉(980px) | 套件成员抽屉 |
| 新建/编辑短表单 | 弹窗 | 新建用例/套件/流水线配置 |
| 危险确认 | 弹窗(420px) | 删除类操作 |
| 登记安装包 | 弹窗 | 从常驻表单改弹窗(见六) |

### 5.2 筛选器布局

- 统一为:左起 类型胶囊组(`.cd-pills`)→ 下拉筛选(模块/平台/包体)→ 搜索框(flex:1, max-width 440px),右端主操作按钮。用例管理的 `.cd-filterbar` 是标准,其他页签向它对齐。
- 搜索输入 300ms 防抖自动触发,保留"重置"清一切;**去掉独立的"搜索"按钮**(有回车兜底即可)。
- 筛选生效时在工具栏下方不另起一行,当前筛选状态由控件自身呈现;有激活筛选时"重置"按钮高亮(描边变 `--brand`)提示可清除。

### 5.3 编辑态 vs 展示态

- 列表 = 展示态,永远只读;编辑入口 = 点行(详情)或操作列(编辑/删除)。
- 编辑一律在弹窗/抽屉里整单提交,不做行内编辑、不做局部保存。
- 详情抽屉里的"展示态"需要跳编辑时:抽屉头部放 ghost"编辑"按钮,点开编辑弹窗(抽屉关闭),保存后重开抽屉刷新。

### 5.4 时间呈现

- 表格时间列一律相对时间(3 分钟前 / 昨天 01:33),悬浮 title 给绝对时间;抽屉/详情里给完整 `toLocaleString`(现状 formatDate 保留用于详情)。
- "下次执行"列:相对时间为主文案 + 到期 1 小时内变 `--warn`。

### 5.5 刷新与实时性

- 不做 WebSocket/自动轮询刷新(工具页,手动刷新足够,避免"AI 式过度工程");保留显式"刷新"按钮,tab 切换时自动重拉该页数据(现状已做)。**例外(2026-09-21 立,2026-09-22 用户拍板提速)**:机器监控页签为 **1s** 轮询(三级提速 5s→2s→1s,MC_POLL_MS=1000,两机 Prometheus scrape_interval 已同步 1s,数字粒度与页面刷新对齐)——时效性指标手动刷新即失去监控意义;轮询仅限该页签激活期间(离开即停),粒度单接口,见 6.9。

**D. 理念逐条映射**(1.1 七条在本页的落点;不适用也写明为什么)

- **理念 1 状态即颜色** → 状态徽标三值映射(good/中性/warn);弃原红码——红=失败语义,验证码不是失败状态,占红即违规。
- **理念 2 密度服务扫描** → 表格 3.2 紧凑档+tabular-nums;全页仅一层极淡阴影;无渐变无插画。
- **理念 3 渐进披露** → 单表 6 列(≤7±2);requestId 等宽 12px muted(低频信息降级);时间列 title 存全量,不另加"剩余秒数"列。
- **理念 4 展示与编辑分离** → 本页纯只读,零编辑控件——旧 P0"防重复提交"作废的根因,理念天然满足。
- **理念 5 每区块一个主动作** → 全页唯一按钮"重新加载"为 ghost:本页无创建类决策区块,不需要 Primary,恢复手段不升格。
- **理念 6 空态是路标** → 空态=状态+原因+预期("约 2 秒自动出现");失败态=原因+重试说明;无插画。
- **理念 7 反馈轻量,异常可见** → 过期/已消费降灰保留不隐藏(recovery codes 实证直用);2s 自动刷新+JSON 比对防重绘;网关不可达给 `.gw-offline` 占位而非白框。
- 结论:七条全部落地,无需修理念。

**旧条目清算**:旧 P0"提交类按钮防重复提交"随功能演化失效(页签现仅剩"重新加载"一个按钮,非提交类);旧 P1 两项(iframe calc 高度/健康条合并)由本节收口。本节改造项由 2026-09-22 任务直接派实现,不计入 P0 合计 12 条口径。

## 八、用例与代码工程的边界(自动化用例:平台管元数据,工程管内容)

### 8.1 结论:平台**不提供**自动化用例的内容编辑(明确"不做")

- **现状问题**:自动化用例的真正编辑发生在 PyCharm/代码工程(`knowledge/swan/cases/driver/**` 的 YAML),平台 case_defs 条目是 sync_cases.py 的**同步副本**。页面上的"编辑 content"改的是库副本,下次同步即被覆盖或形成分叉——这是双头编辑的结构性缺陷,不是加提示能解决的。
- **业界佐证(三家同一答案)**:
  - 禅道 ZTF:脚本头部 `# cid=1` 显式声明禅道用例 ID 作强锚点;脚本只在工程里改,`ztf sync` 把脚本同步成用例,平台做关联与结果回写(脚本为主、用例为辅)。
  - pytest-testrail:测试代码里 `@pytestrail.case('C1234')` 装饰器声明 ID,结果推送 TestRail;TestRail 永远不反向编辑代码。
  - Allure TestOps "Tests as Code":自动化测试以代码仓库为 source of truth,用例由代码生成/同步,手工用例才在平台维护。
- **因此本规范**:
  - 自动化用例的 `content`、标题、类型、标签 = **仓库源头只读**,平台页面不提供编辑入口;
  - 文字用例不受此限,平台全功能编辑(文字用例没有代码副本);
  - 平台对自动化用例的定位 = **目录 + 元数据 + 关联 + 执行结果**,对应"平台管人机交互与结果,代码管内容"的总体架构。

### 8.2 关联的建立:YAML frontmatter 显式 `case_id` 强锚点(推荐做)

- **规范**:仓库 YAML 统一加 frontmatter 字段 `case_id`,值为平台用例编号(与文字用例编号同一命名空间):

```yaml
---
case_id: LOGIN-L2-POS-002
---
# 以下为原有用例内容,平台不解析不改动
步骤: ...
预期: ...
```

- **匹配规则(sync_cases.py 逻辑规范,供开发参考)**:
  1. 优先按 `case_id` **精确匹配**平台条目(强关联);
  2. 无 frontmatter 时回退现有 file_path 路径匹配,并在平台条目上标"弱关联" chip,提示补锚点;
  3. `case_id` 在平台不存在 → 同步报告列出"无效锚点"清单(不自动建条目,防错别字生成垃圾数据);
  4. 一个 YAML 只许一个 `case_id`;一条平台自动化用例只许被一个 YAML 声明(冲突进同步报告)。
- **为什么值得**:现有路径匹配在文件改名/移动时断链,编号后缀匹配(POS-002 撞 LOGIN-L2-POS-002)有歧义;显式锚点同时解决两者,且与 ZTF `cid=`、pytest-testrail 装饰器同构,是业界验证过的最小方案。
- **工程→平台回指:不做 URL,`case_id` 即回指键。** YAML 注释里写平台链接(`http://192.168.12.167:8080/...`)不可取:地址换端口/迁移后全体失效,且污染代码 diff。开发者要找平台条目,拿 `case_id` 到平台搜索框一搜即达(平台搜索已支持编号)——回指体验靠"编号可搜",不靠链接。

### 8.3 平台 → 工程的跳转(详情抽屉)

推荐组合:**"复制路径"为主按钮 + "在 PyCharm 打开"为次按钮**;不做 `file://` 链接。

- `file://` 链接:现代浏览器基于安全策略默认不响应页面内的 file:// 跳转,可靠性差,不做。
- `jetbrains://` 协议:`jetbrains://PyCharm/navigate/reference?project=swan-audio&path=<file_path>` 可直接在装了 PyCharm 的机器上打开文件,体验最好;但仅在装了对应 IDE 的机器生效,失败无反馈。所以放次按钮,容错由主按钮兜底。
- 抽屉内呈现规范(file_path 区块):
  ```
  仓库脚本  knowledge/swan/cases/driver/login/xxx.yaml   [复制路径] [在 PyCharm 打开]
  ```
  - 路径用等宽 12px 展示;复制成功走 toast(4.5),不用 emoji;
  - 文字用例无 file_path,此区块整块不渲染;
  - 弱关联条目在路径旁加"弱关联"chip(2.4 中性灰),点击提示补 `case_id`。

### 8.4 同步策略与一致性提示

| 项 | 规范 |
|---|---|
| 触发 | 手动(用例管理页"同步仓库用例"ghost 按钮,调 sync_cases.py 现有逻辑)为主;**P1** 加定时(每 30 分钟,复用调度器);GitLab webhook 触发等 M3 之后顺路做,不提前 |
| 同步报告 | 同步完成后 toast 汇总:"新增 x · 更新 y · 无效锚点 z · 仓库已删除 n";z/n > 0 时弹抽屉看明细清单 |
| 分叉检测 | content 平台只读后,内容层面天然无分叉,不需要 hash 对比;hash(或 mtime)对比只用于一处:检测**仓库 YAML 已删除/改名**而平台条目仍在 → 条目标"仓库已删除"状态,由人确认后停用,不自动删 |
| 同步状态 chip(列表) | `已同步`(不显示)/ `弱关联`(灰)/ `仓库已更新待同步`(黄,定时同步后消失)/ `仓库已删除`(红)——只在非正常态显示,正常态留白,避免满屏徽章 |

自动化用例(`type=auto`)编辑弹窗:

| 字段 | 平台可编辑? | 说明 |

| 标题 | ❌ | 仓库源头 |

## 九、用例的存储格式与人类交互形态(2026-09-16 用户拍板,最高优先级)

> 一句话:**YAML/CSV 是机器的存储与执行格式;凡与人交互的场景,必须使用人类友好格式。**

### 9.1 四条原则

1. **导入多格式**:同事批量导入用例支持 `.xlsx` / `.csv` / `.md`,只要符合既定模板标准一律支持(SheetJS 等解析库随仓库分发,不依赖外网)。导入前必须预览校验、问题行标红给原因(现有交互不变)。
2. **展示人类友好**:平台所有展示文字用例的地方,采用**表格**或 **xmind(脑图)形式**;禁止把 YAML 原文直接抛给业务同学看。
3. **模板化编辑**:文字用例的新建/编辑在**固定模板**(结构化表单:步骤表格、前置条件、预期结果等字段化控件)中进行并保存;不暴露源格式。
4. **格式转换对人类透明,且中间产物不落地**(2026-09-16 补充收紧:存储格式跟着消费者走):
   - 走**驱动执行**(test_case_driver.py)的用例:YAML 就是程序本身,必须物化成 `knowledge/swan/cases/driver/*.yaml` 进 Git;
   - 走 **.py 脚本路径**(AI 文字→py)的用例:**不落中间 YAML 文件**——AI 直接从平台结构化用例数据生成 .py,一次性转换不留脚手架,避免 .py 与 YAML 双份同步负担;
   - 平台数据库中的结构化用例数据(步骤/动作/数据/预期)是文字用例的唯一权威存储,不额外序列化成 YAML 文件;
   - **反向保证:任何需要人阅读/编辑的时刻,系统负责把结构化数据渲染回人类友好形态。**

### 9.2 落地拆解

| 场景 | 形态 |
|---|---|
| 批量导入 | .xlsx/.csv/.md 模板文件(各给标准模板),预览校验后入库 |
| 用例列表 | 表格(现有) |
| 用例详情/编辑 | 字段化表单抽屉:步骤表格(编号/动作/数据/预期)、可增删行 |
| 用例总览 | 脑图(xmind 形式)按 模块→用例 树状展示,P1 |
| 工程同步 | 平台档案 ↔ YAML frontmatter case_id 强锚点(第八节不变,YAML 仅作存储/执行格式) |

### 9.3 与既有章节的关系

- 第八节"平台管元数据、工程管内容"不变;本节补充:**文字用例**内容在平台侧以人类友好形态维护,平台负责与工程 YAML 的双向转换。
- 批量导入 P0 扩展为:.csv(已上线)+ .xlsx + .md。
