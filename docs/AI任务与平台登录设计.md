## 一、命名与定位

- **页签定稿："AI 任务看板"**（`data-page="tasks"`，页面 id `page-tasks`，新代码 CSS/JS 前缀 `tk-`），nav 插在**首位**（执行会话之前）。v1.0 定名"AI 任务"，v1.1 用户拍板改为"AI 任务看板"。
- **页面形态（v1.2 拍板）：竖版看板**——列=任务状态（待分析/疑问待答/执行中/完成/失败），卡片=任务，**只读**（状态由系统流转，不做拖拽改状态，规范"可拖拽"红线不破）。"AI"前缀是事实陈述（执行者是大领导/小领导 agent），与流水线"最近执行"的任务明确区分，页内文案统一用"任务"。
- 定位：**提交 → 跟踪 → 看报告**的任务工作台。不是运维调度台（不画拓扑、不做实时日志直播），不是项目管理（不做甘特/子任务编排）。核心循环：提交 → AI 分析 → （答疑）→ 执行 → 报告归档 + 群通知。
- **竞品取材（2026-09-30 调研，每家一两点，纪律见规范 1.2）**：Trello（列宽 272px/卡片留白节奏 → 取 264px 档）、Linear（列头=状态名+计数、点卡片开全量详情 → 列头结构与详情交互）、飞书项目（卡片=高频字段集合、"列传达任务流转" → 卡片字段固定三行）、Jira（空列无占位是公认缺口 → 反向印证我们补占位文案）。不取：拖拽换列、可配置卡片字段、空列显隐开关、WIP 限制。

## 二、平台级外壳：登录、左侧边栏、设置

### 2.1 登录（纯用户名，v1.1 拍板重做）

- **机制**：预设 4 个账号 yumiao / fushenghao / wuhouju / menglingzhao（部署侧种子写入 users 表）；**无密码、无任何校验，用户名在预设名单内即登录**。登录两途：点头像卡（一步进）或手输用户名（校验在名单内）。
- **方案裁定**：登录视图仍做在 page.html 内（`body.pre-auth` 隐藏 header/侧边栏/全部页签，仅渲染 `#page-login`），不做独立 login.html——单文件多页签是既定架构，token/组件只维护一份。服务端是真闸门：除 `/api/auth/*` 外全部 API 未登录（无有效 cookie 或用户名不在启用名单）返回 401 `{"error":"未登录"}`；前端显隐只是体验层。
- 前端加载顺序：先调 `GET /api/auth/me`——401 挂 `pre-auth` 且不发起页签数据加载；200 正常初始化。会话中途失效：任意请求遇 401 统一转登录视图 + toast"登录已失效，请重新进入"。

### 2.2 会话机制（给后端的边界）

| 项 | 口径 |
|---|---|
| 会话载体 | cookie `swan_user=<username>`，**只存用户名身份**；HttpOnly + SameSite=Lax。明文即身份（先不做安全是拍板项）；未来要真身份时加 HMAC 签名或服务端 session，UI 不动 |
| 有效期 | 固定 7 天，到期 401 重进 |
| 逐请求校验 | 服务端校验 cookie 用户名在 users 表且 status=active（内存缓存名单即可），否则 401 |
| 退出 | 清 cookie（`POST /api/auth/logout`），无需确认 |
| sessions 表 | **删除**——cookie 即身份，无服务端会话状态可存 |

### 2.5 权限与可见性（v1.1：全员同权，先不做安全）

- **角色概念删除**（v1.0 的 admin/user 两档、权限矩阵整节作废）。理由：无密码体系下"角色"没有信任意义（任何人可以任何身份进），只余 UI 噪音；唯一曾需要角色的入口（账号管理）已收敛进全员可见的设置。
- 全部任务**全员可见**；按人用量报表全员可见；无服务端按人过滤。
- 仅剩一处"本人"语义（是工作流清晰性，不是权限）：**疑问待答**的答复框只对任务提交人本人渲染，其他人见灰字"等待 {username} 答复"。

## 三、任务生命周期与状态机（v1.1：审批闸门删除）

### 3.1 状态枚举与徽标配色（全部走规范 2.2，零新色）

| 状态 | 枚举值 | 徽标文案 | 色系 | 语义 |
|---|---|---|---|---|
| 待分析 | `pending_analysis` | 待分析 | warn 族 | 等大领导分析 |
| 疑问待答 | `questioning` | 疑问待答 | warn 族 | 等提交人答复 |
| 执行中 | `running` | 执行中 | brand（复用 `.running`） | AI 干活中（含 AI 自行处理合并冲突期间） |
| 完成 | `done` | 完成 | good（复用 `.passed`） | 终态 |
| 失败 | `failed` | 失败 | bad（复用 `.failed`） | 终态 |
| 已取消 | `cancelled` | 已取消 | muted（复用 `.cancelled`） | 终态（P1 撤回用） |

- **v1.1 删态**：待审批（`pending_approval`）、已驳回（`rejected`）、待处理冲突（`conflict`）随人工审批闸门一并取消——高风险放行、是否合入主分支、冲突重试还是放弃，全部由大领导/小领导（AI）自主决定，无人工界面。
- warn 族在本模块收敛为两态（待分析/疑问待答），语义仍是"等人"：**黄=等人，蓝=在跑，绿=成了，红=砸了，灰=关了**。
- 完成/失败直接复用 `.passed`/`.failed` 类——与执行会话的结果视觉完全同形。
- 新增 CSS 仅 2 个状态类：`.st-analyze/.st-question { color:var(--warn); background:var(--warn-weak); }`。

### 3.2 状态流转表

| 当前态 | 事件 | 次态 | 触发者 |
|---|---|---|---|
| 待分析 | 分析完成 | 执行中（高风险与否只影响 AI 自身的执行策略，不产生人工态） | 大领导 |
| 待分析 | 提出疑问 | 疑问待答（记录挂起前阶段=待分析） | 大领导 |
| 疑问待答 | 提交答复 | 回到挂起前阶段（待分析/执行中） | 提交人 |
| 执行中 | 执行成功（非代码类） | **完成** | 大领导 |
| 执行中 | 执行成功（代码类，合并成功） | **完成**（merge_status=merged） | 大领导 |
| 执行中 | 执行成功（代码类，合并冲突） | **保持执行中**（merge_status=conflict，由 AI 决定重试或放弃） | 小领导 |
| 执行中 | AI 放弃合并 | **失败**（终态，merge_status=abandoned，失败原因注明"合并冲突未解决，AI 放弃合并"） | 小领导 |
| 执行中 | 执行失败 | **失败**（终态，记失败原因） | 大领导 |
| 执行中 | 提出疑问 | 疑问待答（记录挂起前阶段=执行中） | 大领导 |
| 待分析 | 撤回（P1） | **已取消**（终态） | 提交人 |

```
提交 ─► 待分析 ─分析─► 执行中 ─成功─► 完成(已合并/非代码类)
           │            │  ▲
           │            │  └─合并冲突(AI 重试,任务保持执行中)
           ├─疑问─► 疑问待答 ─答复─► 回挂起前阶段
           │            │
           │            ├─AI 放弃合并─► 失败(终态)
           │            └─执行失败───► 失败(终态)
           └─撤回(P1)─► 已取消(终态)
```

- 疑问可多轮：答复后再次提问则再次进入疑问待答，问答历史全保留。
- 终态只有 完成/失败/已取消 三个；merge_status 是任务属性（merged/pending/conflict/abandoned），不是状态——冲突期间任务仍在"执行中"，避免为 AI 的内部过程造人工态。

### 3.3 分析结论枚举（大领导产出，页面只展示）

- **任务类型**（纯分类，中性 chip）：代码修改 / 测试执行 / 问题排查 / 环境维护 / 其他。
- **风险等级**（severity 型，规范 2.3 风险三档）：高/中/低——**纯展示信息**（提示"这单动了要紧的东西"），v1.0 的"高风险走审批"语义随闸门删除作废；AI 用它决定自身执行与合并策略，不经页面。
- **目标机**：167 平台机 / 176 构建机（显示名与机器监控页一致；分析前为 `-`）。

## 七、刷新轮询与企微通知

### 7.1 轮询（v1.1 保留；v1.2 补看板重绘纪律）

- 显式「刷新」按钮 + 切页签自动重拉（规范 5.5 基线）。
- **15s 轻轮询**（`TK_POLL_MS=15000`，对齐 2026-09-28 对账轮询先例：`reconcileStart` 同款实现，`document.hidden` 即跳过、切走页签即停），重拉**看板**+统计卡+用量表。理由：提交后用户就停在页面上等状态走，AI 任务的状态变化以分钟计，15s 粒度刚好。
- **看板重绘纪律（v1.2，验证码页 6.7 先例）**：重拉前后对任务列表 JSON 做比对，**无变化跳过 replaceChildren**（防整板重绘闪断卡片 hover）；有变化重绘时**保持各列 scrollTop**（记录/恢复列内滚动位置，防止用户正扫到列中部被顶回列首）。
- 抽屉打开期间轮询**跳过抽屉重拉**（防止把用户正在输入的答复文本冲掉），抽屉内给 ghost「刷新」按钮手动更新；看板列本身可照常更新（无输入态）。
- 不做 WebSocket、不做秒级轮询。

### 7.2 任务终态企微群通知（v1.1 新增，后端行为）

- **触发**：任务进入终态（完成/失败）时，由 dispatch_worker/后端调企微机器人向**测试部群**发消息并 **@发布人**。
- **文案**（纯文字，无 emoji 装饰）：`「Swan 测试平台」任务 TASK-20260929-003「修一下登录用例的选择器」已完成`；失败时附一行原因摘要。深链地址 P1 再加（单页应用需先做 `#task=ID` 直达锚点，见 P1）。
- **@人映射**：users 表 `wecom_userid` 列（设置弹窗可编辑，见 2.4）即 username→企微 userid 映射；**未配置映射时降级为发文字消息不 @**，不阻塞任务收尾。
- 群 chat_id 与机器人凭据在后端 `.env.local`，不进 git/文档（团队纪律）。**部署注意**：wecom-cli 现仅本机与 .176 可用，.167（平台机）需先安装方可发群消息。
- 中间态（待分析/疑问待答/冲突处理中）**不发**群消息——群是结果通道不是过程频道；"疑问待答"提醒列为 P1 再议。

## 九、API 形状（前端消费面；worker 内部通道由后端自定，v1.1 审批/冲突接口已删）

```
GET  /api/auth/presets              → {items:[{username,surname}]} (公开,登录页头像卡数据源;v1.2 加 surname)
POST /api/auth/login                {username} → 200 {username,surname}+Set-Cookie | 404 用户名不存在
POST /api/auth/logout               → 200(清 cookie)
GET  /api/auth/me                   → 200 {username,surname} | 401
GET  /api/auth/users                → {items:[{username,surname,wecom_userid,status,created_at}]} (设置弹窗)
POST /api/auth/users                {username,surname?,wecom_userid?} → 201 | 409 已存在
POST /api/auth/users/{name}         {wecom_userid?,status?} → 200 (改映射/停用启用)
GET  /api/tasks/board?q=            → {groups:{pending_analysis:[…],questioning:[…],running:[…],done:[…],failed:[…]},
                                      counts:{pending_analysis:N,…},stats:{running:N,mine:N,done:N,tokens_total:N}}
                                    (v1.2 看板单请求:分组任务+各列计数+统计卡一次拿全;原 bucket/status/page 参数作废)
POST /api/tasks                     {title,description,desired_time?} → 201 {task_id}
GET  /api/tasks/{id}                → 详情(含 questions[],events[],report_md,tokens,产物)
POST /api/tasks/{id}/answer         {answer} → 200 (提交人本人,状态=疑问待答)
GET  /api/tasks/usage               → {items:[{username,submitted,running,done,failed,tokens_total}]}
```

- **看板卡片 item 字段（前端渲染所需最小集）**：`task_id,title,status,task_type,risk,target_machine,submitter,merge_status,created_at,finished_at`。v1.2 变化：加 `finished_at`（终态卡片右侧相对时间）与 `merge_status`（异常徽标判断，列表层即需）；**去掉 `tokens_total`**（卡片不放 token，用量在 stats/usage）。report/questions 等仍只在详情返回。
- 分组内每列最多返回 50 条（created_at 倒序），`counts` 给全量计数（列尾"共 N 条"与列头计数用）。后端可按此形状实现，前端承诺只消费上述字段。
- v1.1 删除的接口：approve/reject/merge-retry/merge-abandon（AI 自主，走 worker 内部通道，不经 HTTP）；admin 类角色参数全部消失。
- 企微群通知是后端内部行为（终态钩子），无前端 API。

## 十一、理念映射（规范 1.1 七条逐条，v1.2 看板口径）

- **理念 1 状态即颜色**：六态全走 2.2 表零新色；列头色点/卡片徽标同源同色；warn 族"等人"两态；done/failed 复用 `.passed/.failed` 与执行会话同形；头像/项目块不做按人配色。
- **理念 2 密度服务扫描**：卡片三行封顶、字段取舍有明文理由表（4.2）；任务号/分支/token 明确不上卡；时间 tabular-nums；无插画无渐变。
- **理念 3 渐进披露**：卡片只留扫描层（标题+徽标+人/机/时间），问答/报告/产物/分析说明/任务号全在抽屉——点卡片是唯一披露动作。
- **理念 4 展示与编辑分离**：看板只读、不拖拽改状态；作答是抽屉里的显式动作块；合并过程 AI 自主，页面零写入口。
- **理念 5 每区块一个主动作**：工具栏 Primary=提交任务；提交弹窗 Primary=提交任务；抽屉疑问块 Primary=提交答复。各块不叠加；列头不可点不折叠。
- **理念 6 空态是路标**：看板全空=一行灰字"还没有 AI 任务，点右上角'提交任务'把活派给 AI"；单列空="暂无任务"；筛选无结果/加载失败三分文案；报告区执行中给预期文案。
- **理念 7 反馈轻量，异常可见**：全 toast；15s 轮询仅页签激活且比对防重绘；merge 异常徽标只在 conflict/abandoned 出现；失败原因、问答历史终态后全部保留；**终态企微群通知是本条的平台级延伸**——失败也是数据，送到人眼前而不是等人来查。
