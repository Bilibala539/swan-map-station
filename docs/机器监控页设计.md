# 机器监控页设计（"机器监控"页签）

> 2026-09-21 v1.0，产品设计师产出。依据 `docs/平台UI设计规范.md`（下称"规范"）。
> 技术栈已拍板（不在本稿裁决范围）：Node Exporter + Prometheus（9090 仅本机）+ 平台后端代理 `/api/metrics/*` + page.html 新页签原生图表；Grafana :3000 独立深度大盘，平台内只做入口链接。
> 监控对象：167（平台机）/ 176（构建机）两台 Linux。

---

## 一、命名与定位

- 页签定稿：**"机器监控"**（`data-page="machines"`），nav 插在"用例历史"与"验证码工具"之间（工具类页签区段）。
- 命名理由：与现有页签命名语言一致（执行会话/包管理/测试套件——名词直给，零术语门槛）；"节点监控"是 Prometheus 术语不进 UI；"资源监控"过泛。
- 定位：**低频巡检 + 出事细看**的工具页——跑测试/打包前瞄一眼资源余量，打包失败时排查是否构建机磁盘/CPU 顶满。不是运维大屏，一切按规范"数据优先，装饰最小"。

## 二、布局：**上下两卡，每卡四格平铺（不做左右分栏、不做折叠展开）**

### 2.1 整页结构

```
工具栏：左 = 页面说明 meta（"167 平台机 / 176 构建机，1s 自动刷新"）
        右 = ghost"刷新" + ghost"Grafana 大盘"（新窗口，title 说明）
卡片一：平台机 167
卡片二：构建机 176
```

**为什么上下两卡、不左右分栏**：主内容宽 1240px，左右分栏每栏仅 ~610px，四格 + sparkline 每格被压到 ~280px 宽，15min 走势挤成噪音；且两台机角色不同（平台机稳态服务 / 构建机打包重负载），是"各看各的仪表"而非"A/B 逐格对比"——严格行对齐的价值撑不起分栏的宽度代价。上下布局每卡全宽，一卡高度 ~240px，两卡 + 工具栏在 1440×900 首屏内完整可见。

### 2.2 单卡结构（每台机一张 `.card`）

```
┌ 卡头 ────────────────────────────────────────────────┐
│ ●平台机 167   负载 0.42/0.38/0.31 · 已运行 23 天      │  ← 状态点+机器名+负载三值+uptime（meta 13px）
├ 四格 grid（2×2 或 1×4，卡宽自适应）────────────────┤
│ CPU          内存            磁盘           网络      │
│ 12.4%        3.2G / 7.8G    （占用条×N）     ↑412KB/s  │
│ [sparkline]  [sparkline]     根分区 41%     ↓96KB/s   │
│              41%             /opt   67%     [sparkline]│
└──────────────────────────────────────────────────┘
```

- **CPU**：数字 = 整机利用率%（22px stat 风格）+ meta"16 核"；sparkline 近 15min。
- **内存**：数字 = used/total + 百分比；sparkline 近 15min（画占用率 %，实现备案 2026-09-21——与字节走势同形状，% 更利于判读逼近上限）。
- **磁盘**：**不画走势图，占用条按数据渲染**（主会话裁决 2026-09-21：后端按实际挂载点返回 disks[]，/opt 与 / 同设备（两台机现状）时只有一行，不同设备才两行——渲染跟着数据走，布局理由不变）：`挂载点名 used/total + 进度条 + %`。理由：容量型指标趋势意义弱（一天涨一点，15min 走势近乎直线没信息量），"还剩多少"才是装机/打包前真正要看的问题；占用条 + 阈值换色（见五）一眼可判。
- **网络**：数字 = 当前 ↑/↓ 速率（自动选 KB/s 或 MB/s）；sparkline 近 15min（只画下行或上下两线同图，取上下两线同图、↓ 用 ink、↑ 用 brand——纯分类双色，不占语义色）。
- **负载/uptime**：放卡头 meta 文字（"负载 0.42/0.38/0.31 · 已运行 23 天"），不单独占格——负载三值是判读 CPU 的辅助上下文，放数字旁边正合适，单独画图是浪费。
- 单卡四个维度**全部首屏平铺，无折叠展开**。理由：只有两台机器，明细总量固定且小；折叠是"为做而做"的交互（规范反过度设计），藏起来的监控数据等于没有。

## 三、图表选型与刷新（结论 + 理由）

### 3.1 画法：**原生 SVG 面积 sparkline，不引 ECharts**

- 实现：`drawSparkline(svgEl, points, opts)` 一个函数（~40 行原生 JS），`<polyline>` 画线 + 同色 8% 透明度 `<polygon>` 填充。
- 理由：
  1. 数据量小：15min 走势取 **60 点**（step 15s 的 range query，与 scrape 同步无损采样；原 30 点@30s 口径经 step 分叉裁决 2026-09-21 作废，见 3.2），SVG 毫无压力；
  2. 样式完全跟随 CSS token（线色按维度指定、填充同色弱透明），主题一致，不受图表库主题体系绑架；
  3. 零依赖零加载成本——ECharts 单文件 ~1MB，为 6 条迷你图引入得不偿失，且图表库会诱惑后续页面堆可视化（防"AI 味"红线：不做运维大屏化）；canvas 需自理 DPR 缩放，SVG 免掉；
  4. 符合规范"不引组件库 / 禁外部 CDN / vendor 本地"既定路线。
- 形态：**面积图（线 + 淡填充），不用纯线条 sparkline**——1s 高频刷新下纯线条视觉抖动感强，面积填充锚定"当前值到基线"区域，趋势与"逼近上限"读得更准。
- 磁盘不用图，占用条用纯 div（宽度 % + 语义色）。

### 3.2 刷新：**1s 轮询，仅本页签激活时**（2026-09-22 用户拍板三级提速 5s→2s→1s，MC_POLL_MS=1000）

- 页签激活时拉取并 `setInterval` 1s 轮询 `GET /api/metrics/summary`（一次返回两台机全部首屏指标 + 各机采集状态，前端一次 fetch 渲染两卡）；离开页签 `clearInterval`。两机 Prometheus scrape_interval 已同步 1s，数字粒度与页面刷新对齐。
- **规范 5.5 例外声明**：5.5"不做自动轮询"针对业务列表数据（监控列表用手动刷新足够）；本页签数据是**时效性指标，手动刷新使监控失去意义**——轮询范围仅限本页签激活期间，粒度 1s、单接口，成本可控。已在规范 5.5 加例外括注（2026-09-22 更新为 1s）。
- 走势数据**由后端 Prometheus `query_range` 提供**，前端不自累积点（否则刷新页面走势全丢）。主会话裁决 2026-09-21：history 接口**一次拉该机全部指标**（`GET /api/metrics/history?machine=&range=15m`；实现备案：metric 参数可选，缺省一次返回 cpu/mem/net_up/net_down 全量），与 summary 分开 30s 一拉。step 定稿 **15s 共 60 点**（step 分叉裁决 2026-09-21，改稿保实现 METRICS_STEP_SECONDS=15）：step 与 scrape 同步才是无损采样——step 30s 在 15s scrape 下丢一半采样点，会抹平 176 打包时的资源尖峰（恰是本页核心排查场景），而省流量收益仅 KB 级不成立；原 30 点@30s 口径作废。

### 3.3 后端接口形状（给开发，命名与字段建议）

- `GET /api/metrics/summary` →
  `{"machines":[{"machine_id":"176","role":"build","instance":"192.168.12.176:9100","timestamp":ts,"up":true,"cpu_percent":12.4,"cpu_cores":16,"mem_percent":41.2,"mem_used_bytes":...,"mem_total_bytes":...,"disks":[{"mount":"/","used_bytes":...,"total_bytes":...,"percent":41}],"net_up":...,"net_down":...,"load":[l1,l5,l15],"uptime_s":...}, ...]}`（15 字段，无 status）
- 契约定稿（收口裁决 2026-09-21）：**无 status 字段，后端无状态**（不缓存、不做状态机）；`up=true` 当 target up=1 或任一核心指标有值（兜底 up 序列未生成的情形）；失联机指标为 null、disks=[]、up=false——失联/滞后卡态全部由前端判定（见 §四）；字节量字段统一 `_bytes` 后缀；disks 按 device 去重（/ 与 /opt 同设备只返回一行，留根分区）。
- Prometheus 查询口径：CPU=100−idle（`node_cpu_seconds_total` rate）；内存=MemTotal−MemAvailable；磁盘=`node_filesystem`，fstype 过滤伪文件系统（`fstype!~"tmpfs|overlay"`，实现口径纠正 2026-09-21——tmpfs/overlay 是 fstype 标签不是 device 标签），挂载点取 `/` 与 `/opt`；网络=`node_network_*_bytes_total` rate 排除 lo；负载=`node_load1/5/15`；uptime=`node_boot_time_seconds`。
- 机器清单来自**后端配置**（写死或配置文件两台），不做页面增删管理——两台固定机器配 UI 管理是过度设计。
- Prometheus 地址写后端配置（localhost:9090），凭据/地址不进前端。

## 四、状态设计

| 状态 | 呈现 |
|---|---|
| 正常 | 卡头绿色状态点（`--good`）；四格照常 |
| **单机失联**（**前端判定**：`up===false`；收口裁决 2026-09-21 后端无状态无 status） | **仅该卡降级，另一卡正常渲染**：卡头状态点变 `--bad` + 失联 chip（`--bad-weak` 底"失联"）；四格区域替换为一行灰字"采集失联：无法连接 node_exporter"+ ghost"重试"。起始时间（"自 14:32 起"）仅当页面打开后发生的失联才显示（前端会话内记录，进页前已失联则不显示） |
| 数据滞后（**前端判定**：`up!==false` 且 summary.timestamp 与本地时间差 >30s（MC_STALE_SECONDS）） | 数据照常显示 + 卡头黄色 chip"数据滞后" + meta 显示数据时间；滞后的数字必须可见时间戳，防误读为实时 |
| 加载态 | 首次进页签：每卡区域一行灰字"加载中…"（沿用全站惯例，不做骨架屏） |
| 空态（Prometheus 刚装，尚无数据点） | 各格显示"—"；卡头 meta 提示"等待首次采集（约 1-2s）"，不需要专门空态插画 |
| 轮询连续失败 ≥3 次 | 深色失败 toast 一次"监控数据获取失败"，状态行降级；**不逐次弹 toast**（防打扰），恢复后成功 toast 一次 |

- 单机故障不拖垮整页是硬要求：后端代理对两机**独立超时捕获**，summary 按机返回 up 与指标（无 status，卡态全部前端判定）——绝不因 176 挂了让 167 的卡片也白屏。

## 五、视觉与防"AI 味"自查

- **不画圆环 gauge**——gauge 是运维大屏的"一眼 AI"重灾区，数字+sparkline 信息等量更紧凑。
- 阈值换档是**硬切不是渐变**：CPU/内存/磁盘占用 <70% 用 `--ink` 中性条、70–90% `--warn`、>90% `--bad`；不搞绿黄红连续渐变条。
- 数字变化无 transition/翻牌动效；sparkline 重绘不 tween——1s 一跳的页面加动画纯属噪音。
- 不做深色大屏风、发光描边、卡片内部再嵌"子卡片"阴影层次；沿用规范圆角/阴影/边线既有档位。
- 空态无插画；文案用测试工程师语言（"采集失联：无法连接 node_exporter"，不写"监控 hippo 离线中"式卖萌，也不写"智能资源洞察"）。
- 图表线色：CPU 用 `--brand`、内存用 `--good`、网络下行 `--ink`/上行 `--brand`——仅作分类区分，**不挪用红黄语义色**（红黄只属于状态，见规范 2.1）；失联/滞后状态用 chip 表达而非曲线变色。
- 字体：数字沿用 stat-value 风格 22px；sparkline 无坐标轴无刻度文字（hover title 给历史值即可，P1）。

## 六、P0 / P1 / 明确不做

**P0**
1. nav 加"机器监控"页签（用例历史与验证码工具之间）；
2. `/api/metrics/summary` + `/api/metrics/history` 两路由（独立超时、按机返回 up/指标——卡态全部前端判定、机器清单走配置）；
3. 上下两卡 + 四格平铺（CPU/内存 sparkline、磁盘占用条（数据驱动）、网络速率+sparkline）+ 卡头负载/uptime；
4. 1s 轮询（仅激活时）+ SVG 面积 sparkline 绘制函数；
5. 失联/滞后/加载/空态四态 + 失败 toast 节流；
6. 工具栏 ghost"刷新" + ghost"Grafana 大盘"（新窗口外链）。

**P1**
- 构建事件叠加：176 的 sparkline 上标注打包时段（依赖打包事件时间戳接入，高价值，等打包链路数据可查后做）；
- hover sparkline 显示对应时刻数值；
- 时间范围切换（15min/1h/6h）；
- 磁盘 inode 使用率（/opt 大量小文件场景）。

**明确不做**
- 圆环 gauge、深色大屏、WebSocket 推送、可拖拽/自定义卡片布局、机器增删管理 UI、告警阈值配置 UI（告警需求出现时另行提案）、页面内嵌 Grafana iframe（拍板已定：独立入口链接）。
