# UIAutotest 多 Agent 编排体系

> 本文档面向人类读者，介绍 UIAutotest 项目的多 Agent 协作架构。
> 机器可读的实现细节在 `.claude/agents/*.md` 和 `.claude/commands/*.md`。

---

## 一、团队架构

```
用户需求（一句话 / 文字用例 / Excel）
  │
  ▼
┌────────────────────────────────────────────────────────┐
│                  orchestrator（主会话）                  │
│                                                        │
│  职责：拆解意图 → 路由模式 → 派发 agent → 汇总交付     │
│  工具：Agent / SendMessage / TaskCreate / MCP 知识库    │
└───┬─────────┬─────────┬─────────┬─────────┬───────────┘
    │         │         │         │         │
    ▼         ▼         ▼         ▼         ▼
┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────────┐
│explorer│ │element│ │codegen│ │verify │ │spec-keeper│
│探索App │ │截元素  │ │写代码  │ │跑验证  │ │管规范     │
└───────┘ └───────┘ └───────┘ └───────┘ └───────────┘
```

**关键原则**：orchestrator 不写代码、不直接操作测试平台，只做分派和汇总。

### 生命周期

| Agent | 派发方式 | 特点 |
|-------|---------|------|
| explorer、spec-keeper | SendMessage（长驻） | 双向通信，积累上下文，支持多轮交互 |
| element、codegen、verify | Agent()（一次性子 agent） | 每次干净上下文，执行完毕即销毁 |

**选择依据**：探索性/积累性任务用长驻，任务明确/产出确定的用一次性。

## 二、三种编排模式

orchestrator 收到需求后，按关键词匹配选择模式：

| 模式 | 触发场景 | 产出 |
|------|---------|------|
| convert-cases | "写用例""转自动化""覆盖XX功能" | pytest 可执行脚本 |
| enrich-kb | "探索""补充知识""更新页面" | 知识库 pages/*.md 更新 |
| fix-batch | "失败""修复""fix""红了" | 修复后的通过用例 |

---

## 三、convert-cases 流水线

文字用例 → 可执行 pytest 自动化脚本的完整流程。

```
Step 1: 知识库预检（orchestrator）
  查 MCP 知识库，确认目标页面是否已探索
  ├─ 已有 → 跳 Step 2
  └─ 缺失 → 进 Step 2

Step 2: explorer 确认页面路径
  产出：pages/*.md + app_map.json 更新

Step 3: element 定位/截取元素
  方式：ShowUI-2B 自动定位 → 精修 bbox → 裁剪 → 质量校验
  产出：image_ai/*.png + image_name_mapping.py 新常量

Step 4: codegen 生成代码
  产出：基础 AW 调用 + TidiTree 业务方法 + pytest 用例
  前置：通过 G1-G5 门禁

Step 5: verify 验证
  产出：pytest 运行报告 + 图片转正(image_ai → image)
```

---

## 四、派发前门禁（G1-G5）

spawn codegen 前 orchestrator 逐项检查：

| # | 检查项 | 不过则 |
|---|--------|-------|
| G1 | 页面已在知识库 | 先派 explorer |
| G2 | 元素图片已注册 | 先派 element |
| G3 | 任务含清理逻辑 | 补充后再派 |
| G4 | 清理后回首页 | 补充后再派 |
| G5 | 一个 py 一个 test 方法 | 拆分后再派 |

## 五、知识注入

orchestrator 用 MCP 查询本次任务相关上下文，注入子 agent prompt：

```python
related_pages  = get_related_pages("目标 page_id")
nav_path       = get_navigation_path("消息列表页", "目标页面")
similar_tests  = find_similar_tests("当前用例功能描述")
experience     = semantic_search("功能描述", source_type="docs")
```

只注入相关片段，不灌全量知识库。

## 六、失败回退策略

verify 报告失败时，orchestrator 按错误类型回退：

| 失败类型 | 回退目标 | 说明 |
|---------|---------|------|
| 图片匹配失败 | element | 重新截图 |
| AW 逻辑错误 | codegen | 重写代码 |
| 页面对不上 | explorer | 重新探索 |
| 框架层问题 | 用户 | 由用户决策 |

最多回退 3 次，仍失败则整理诊断交回用户。

## 七、enrich-kb 模式

不写自动化用例，只补充/更新应用知识。

| 子模式 | 触发 | 流程 |
|--------|------|------|
| new-page | 知识库没有的页面 | explorer 探索 → 审核 draft → 转正 pages/ |
| update-page | "XX变了""改版了" | explorer 对比验证 → 覆写 pages/ |
| add-feature | 跨页面功能记录 | 多页面探索 → 整合 digest/ |
| audit-kb | "巡检""检查准确性" | verify 逐页验证可达性 → 汇总报告 |

---

## 八、fix-batch 模式

已有用例失败的诊断和修复流程。详细编排见 `.claude/commands/fix-batch.md`。

```
Phase 0: 失败聚类分析（按根因分组 → 排优先级）
Phase 0.5: 共性根因分析（同一 AW 方法导致多个失败 → 一次修好）
Phase 1: 逐个修复
  Step 0: 代码-用例一致性校验（不一致则删除重建）
  Step 1: verify 诊断根因
  Step 2: 按根因派修复 agent
  Step 3: verify 重跑验证（最多 3 轮）
  Step 4: 修公共方法后跑同组用例（附带修复检查）
Phase 2: 汇总报告
```

## 九、子 agent 通信协议

### 派发格式（orchestrator → 子 agent）

```
任务：<动词开头一句话>
目标功能：<功能点描述>
相关上下文：<知识注入片段>
完成标准：<什么算完成>
```

### 回报格式（子 agent → orchestrator）

```
[完成] 或 [失败]
文件变更：
  - <路径>（<描述>）
新增图片常量：<列表> 或 无
建议 verify 命令：pytest <路径> -v
遗留问题：<内容> 或 无
```
