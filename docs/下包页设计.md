## 一、定位与页签决策：~~新页签，不并入包管理~~（**已废止**，见顶部状态框）

本节理由保留作设计推理记录，**不再有效**：

理由：

1. **受众不同**。包管理页签服务于"管包的人"（登记、看来源、看执行次数、删记录）；本页服务于"要装机的人"（测试/产品/开发拿包装手机），后者不该理解登记表单和来源字段。
2. **交互形态不同**。本页是纯只读分发页，核心动作是"扫码 + 下载"，需要大尺寸二维码直接可见；塞进包管理的管理表格会让操作列变成 下载/二维码/查看执行/删除 四连，且登记弹窗、删除确认与高频扫码动作挤在一屏。
3. **成本可控**。两个页签读同一张 apks 表、同一个 `/api/apks`，无数据分叉。

配套裁决：**包管理页签不另加二维码/下载入口**，本页是唯一分发出口——避免双入口双维护（规范"不过度设计"精神）。
> **2026-09-20 废止注记**：合并后包管理页列表操作列即含二维码/下载/查看执行/删除，本配套裁决同步作废。

## 二、数据与接口缺口（后端 P0）

现状 `apks` 表：`apk_id / app_version / branch / commit_hash / flavor / source / file_path / file_hash / notes / registered_at`。对照需求：

| 需求 | 现状 | 缺口 |
|---|---|---|
| 下载到电脑 / 扫码下载 | `file_path` 只存服务器本地路径，**无任何 HTTP 下载端点** | 新增下载端点 |
| 分支号 | `branch` ✅ | 无 |
| 打包时间 | 只有 `registered_at`（登记时间） | 新增 `build_time` 字段 |
| 正式服/测试服 | `flavor` 是渠道/构建变体维度（release/debug 等），值域不规范且语义上不等于服别 | 新增 `server_type` 列（formal/test），服别以列为准 |

### 2.1 下载端点

`GET /api/apks/{apk_id}/download`

- 查库取 `file_path`：文件存在 → 返回文件流，`Content-Type: application/vnd.android.package-archive`，`Content-Disposition: attachment; filename="<apk_id>.apk"`（attachment 保证电脑浏览器触发"保存"，手机浏览器触发下载，一个 URL 两端通用）。
- 文件不存在 / apk_id 不存在 → 404 + `{"error": "文件已清理或不存在"}`（前端转 toast）。
- 服务器是 BaseHTTPRequestHandler 手写路由，在 `do_GET` 里加 `startswith("/api/apks/") and endswith("/download")` 分支，仿照现有 `/api/cases/.../history` 的取参写法；文件流式读写（apk 几十 MB，勿整体读进内存）。
- 内网工具，不做鉴权（平台账号体系未建，保持现状）。

### 2.2 列表响应补三个字段

`GET /api/apks` 每条 item 追加：

- `download_url`：**后端按请求 Host 生成绝对 URL** `http://{Host}/api/apks/{apk_id}/download`。Host 取请求头（含端口）。为什么由后端拼：多网卡/换端口/反代场景后端最清楚哪个地址对外可达，且手机扫码访问的 URL 必须与电脑访问同一 host 才可达。`X-Forwarded-Host` 支持留 P1。
- `file_exists`：`os.path.isfile(file_path)`。测试包会被定期清理，登记记录还在而文件已删是常态——没有这个字段，扫码的人会扫出一个 404。50 条内逐行 stat 无性能压力。
- `build_time`：原样返回（见 2.3），展示层做回退。

### 2.3 打包时间字段

- `ALTER TABLE apks ADD COLUMN build_time TEXT NOT NULL DEFAULT ''`。
- `register_apk` payload 支持 `build_time`（ISO 字符串）；`build_swan_apk.py` / `register_apk.py` 登记时传打包完成时刻；手动登记未传时留空。
- 展示规则：`build_time` 为空回退显示 `registered_at`（旧数据自动兜底），不做数据回填。
- 注意 2.3 与 2.2 的返回分开：接口返回原始值，"回退"逻辑放前端展示层。

### 2.4 服别字段 server_type（以列为准，不做 flavor 映射）

- `apks` 表加 `server_type TEXT NOT NULL DEFAULT 'test'`，值域只有两个：`formal`=正式服、`test`=测试服。
- 写入链路：打包脚本 `--server-type` 参数传入（build_swan_apk.py / register_apk.py 透传到登记 payload）；不传默认 `test`，存量行由列默认值 `test` 兜底——**不会出现未分类**，故页面不设"未分类"胶囊。
- `flavor` 保留为渠道/构建变体维度（release/debug 等），与服别互不干扰、互不映射。
- 展示规则：`formal` → "正式服" chip；**其余一律按"测试服"呈现**（值域收敛在写入侧，展示侧不做第三态）。

## 三、页面布局

自上而下三段：

### 3.1 工具栏（规范 5.2 标准结构）

- 左：**服别胶囊组**（`.cd-pills` 样式，带计数）`全部 23 / 正式服 8 / 测试服 15` → **分支下拉**（distinct branch，"全部"默认）→ **搜索框**（flex:1 max-width 440px，匹配包 ID/版本/分支/Commit，300ms 防抖自动触发，无独立搜索按钮）。
- 右：**刷新**（ghost）。本页没有创建类主操作，Primary 留给卡片的"下载"按钮（见 3.2）；有激活筛选时"重置"高亮描边 `--brand`（规范 5.2）。
- 计数为当前数据集内统计（页签加载时拉 `limit=200`）。

### 3.2 最新可用安装包（两张卡，本页主场景）

装机的人 90% 的诉求是"装最新的正式服/测试服包"，不该在表格里找第一行再点弹窗。参考规范七 Nexus 的"Latest 置顶"对标，落到卡片：

- 区块标题：`最新可用安装包`（17px/600）+ 一行 hint："按服别取文件仍可下载的最新包；全部历史见下表"。
- **取法**：按 `server_type` 分组，每组取 `file_exists=true` 中时间（build_time 回退 registered_at）最新的 1 条。**跳过文件已清理的包**——卡片区叫"最新可用"，宁可下钻也不要给出扫不出来的码。
- 两卡并排 `grid 2 列`（<800px 单列）；某服别无可用包时该卡位渲染一行灰字"暂无正式服包（可能已清理）"，不渲染空卡。
- 卡内结构（左信息右码，flex）：

```
[正式服 chip]  swan-main-4d1ed7b-20260919        ← 包 ID，等宽 12px
版本 5.3.0 · 分支 main · Commit 4d1ed7b          ← meta 13px muted
打包时间 2 小时前（title=完整时间）
                                                 
[下载] [二维码放大]        [二维码 160px]
```

- 下载按钮 Primary（每卡一个区块，合规规范 4.1）；"二维码放大"ghost，点开 3.4 弹窗。二维码 160px 手机能直接扫，放大是近距离扫不动的兜底。
- 卡片遵循规范圆角 12px / 阴影一档 / 无渐变无图标。

### 3.3 全部安装包表格

`.card.table-card` 标准表格，规范 3.2 紧凑档全适用。列定义：

| 列 | 内容 | 呈现规则 |
|---|---|---|
| 服别 | chip | `server_type` 列直出（formal→正式服 / 其余→测试服），配色见 4.1 |
| 包 ID | 等宽 12px | 全站主键列规范 |
| 版本 | 文本 | |
| 分支 | 文本 | 需求字段 |
| Commit | 等宽 12px | |
| 打包时间 | 相对时间 | `build_time` 空回退 `registered_at`；title 给完整时间（规范 5.4）|
| 操作 | `下载` `二维码` | ghost 行内按钮（5px 10px / 12px），不做图标 |

- 默认按时间倒序（最新在顶），行首不加"最新"小标——卡片区已承担该职责，表格只管全量历史（与规范 6.2 包管理的"最新"标不冲突，那是管理页签的规则）。
- 分页沿用 `.cd-pager`；数据 ≤ 每页 30% 时隐藏。
- 表格行不做点击详情（只读页，notes/source 等次要信息放二维码弹窗 meta，不值得开抽屉）。
- **文件已清理的行**：下载/二维码按钮禁用置灰，title"文件已清理"；该行其余文字不做整行降灰（包 ID/版本仍是有效元数据）。

### 3.4 二维码弹窗（Modal，420px 档）

```
swan-main-4d1ed7b-20260919          ← 标题，等宽 14px
版本 5.3.0 · 正式服 · 分支 main · 2 小时前    ← meta 13px muted
备注：xxx（有则显示）

            [二维码 260px]
下载地址  http://192.168.12.167:8080/api/apks/swan-main-4d1ed7b-20260919/download
          [复制链接]

仅支持 Android 安装；iOS 扫码可打开链接但无法安装 apk
[下载到电脑]  [关闭]
```

- 大码 260px（放大兜底 + 手机可扫）；下载地址等宽 12px，"复制链接"成功走 toast（规范 4.5 / 8.3 同款交互，不用 emoji）。
- 弹窗支持点遮罩 / Esc 关闭（规范 4.3 的 Esc 缺口，本页弹窗实现必须带）。
- 不套弹窗。

## 四、交互细节

### 4.1 服别 chip 配色（裁决）

| 服别 | 样式 |
|---|---|
| 正式服 | `--neutral-weak` 底 + `--ink` 字 + `1px solid --ink` 描边 |
| 测试服 | 普通中性 chip（`--neutral-weak` 底 + `--muted` 字） |

理由：全站四个语义色（红绿蓝黄）已被执行状态占用，规范 2.1 明令"颜色即状态，不挪作他用"；服别又没有好坏语义（规范 2.4"纯分类用中性灰"），**不该也不必引入新颜色**。但装错包有真实事故成本（测试包装上演示机），防呆靠两层：chip 文案直书"正式服/测试服"+ 正式服描边加重一级形成视觉锚点。不叠感叹号、不加图标。

### 4.2 下载与复制反馈

- 下载是浏览器原生行为，无 JS 回调，不做 toast；按钮防重复提交不适用（导航型）。
- "复制链接"成功 → 深色 toast"链接已复制"2.4s。
- 下载请求失败（文件在列表后、点击前被清理）→ 失败 toast"文件已清理，无法下载"3.5s。

### 4.3 筛选联动

- 胶囊 / 分支 / 搜索三者 AND 组合，纯前端过滤当前数据集（200 条内不需要后端过滤）。
- 刷新与页签切换重拉数据，保持当前筛选与页码（规范 5.5）。

## 六、iOS 呈现裁决

当前产物只有 Android APK，**不做平台区分逻辑**（不做 UA 检测、不做双端分流——数据上无 iOS 包可给，检测是空转）。用两处静态文案管理预期：

1. 二维码弹窗内一行（扫码前最后确认点）："仅支持 Android 安装；iOS 扫码可打开链接但无法安装 apk"。
2. 无需在页头/卡片区重复——扫码的人必然经过弹窗或卡片，一处足够；页头再放是噪音。

iOS 实际体验（相机扫码 → Safari 打开 → 下载失败）由浏览器行为决定，页面侧无可为，文案如实说明即可。未来若出 ipa 产物，再按平台列拆分（远期，不设计）。

## 七、二维码技术策略

- **URL 策略**：二维码内容 = `download_url`（后端按请求 Host 生成，见 2.2）。前端兜底：响应缺 `download_url` 时用 `window.location.origin` 自拼同路径。
- **为什么直链、不做 H5 落地页**：直链在 Android 上扫码即下载，路径最短；H5 落地页（扫码进一个包详情页再点下载）多一次点击、多一个服务端渲染面，当前只有单平台产物，收益为零——列入"明确不做"，将来多平台产物共存时再评估。
- **生成方式**：前端本地库生成，`dashboard/vendor/qrcode.min.js`（**随仓库分发，禁外网 CDN**，同 SheetJS vendor 先例；选 MIT 许可、无依赖的成熟实现）。平台在内网(.167,.166 已退网)，浏览器机器未必有外网。
- **二维码参数**：尺寸按 3.2/3.4 两档；纠错等级 M；`download_url` 约 70-90 字符，M 级纠错下 260px 清晰可扫，无需更长 URL 时压缩。
