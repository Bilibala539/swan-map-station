## 2. 目标架构:控制面 / 执行面分离

```
人 → 平台页面(包管理/用例/套件/流水线配置,所有"操作"入口)
        │  平台触发 Jenkins REST API(带参数:branch/suite_id/apk_id)
        ▼
   Jenkins(执行层,.166:8082,计划任务常驻)
     ├─ 打包 job:拉源码(auto_tester)→ flutter build → POST /api/apks 登记 → 触发测试 job
     └─ 自动化 job:pytest(conftest 照常向平台设备池 acquire/release)→ 结束回调平台
        │  状态回调 + 平台侧轮询兜底
        ▼
   平台: pipeline_jobs 记 jenkins job/build 号,状态同步;执行会话/历史/证据/建单链路不变
```

- 平台管:人机交互、配置(套件/流水线/频率)、设备池、结果与证据、禅道建单
- Jenkins 管:构建执行、任务排队、重试、多项目 job 复制
- 设备分配始终走平台设备池,Jenkins 不做设备管理——多设备并行 = 多个测试 build 各领一台

## 3. 触发矩阵(所有执行入口)

| 触发源 | 方式 | 落点 |
|---|---|---|
| 页面手动 | 套件/流水线页"立即执行" | POST run → Jenkins |
| 定时 | pipeline_configs:单次/每天/每 N 天/每周几 + 开始时间 | scheduler 30s 检查 → 触发 |
| 新代码合入 | Jenkins job 轮询 SCM(auto_tester 凭据)或后续 webhook | 打包 job |
| 新包产出 | 打包 job 成功后下游触发冒烟 | 测试 job(冒烟套件) |
| 夜间回归 | 现有 nightly 改为按"全量回归套件" | 测试 job |
